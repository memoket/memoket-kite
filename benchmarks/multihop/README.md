# Multihop 实验约束与推进顺序

完整迭代记录、负面结果及采用／撤销决策见 [EXPERIMENT_LOG.md](EXPERIMENT_LOG.md)，
逐轮数值、冻结摘要和历史用量快照见 [EXPERIMENT_RESULTS.json](EXPERIMENT_RESULTS.json)。

MuSiQue 的整段建库和问答入口见 [musique/README.md](musique/README.md)。

路径：**单轮 Extract → Compile 与原生检索 → Answer 一次**。
原基线和单轮修正版保持 Compile 一轮。最新用户授权的反馈实验最多三轮 Compile，每轮候选仍为一，
后续 Compile 读取实际取回的证据并修订完整原生计划；最后只调用一次 Answer。
Extract 使用 gpt-6-luna、reasoning_effort=none、temperature 0；Compile 使用 gpt-6-luna、medium reasoning。
Answer 使用 gpt-4o-mini、temperature 0。提取缓存和建库来源检查区分 reasoning 设置，不能把 medium 的旧响应当成 none。
三组共用 profile、提示词、预算、失败处理。LoCoMo / LongMemEval 的 binding 保持不变。

当前候选通过 `evaluate --compile-rounds 2` 启用有界反馈；也可测试上限三轮，默认一轮保持历史控制。
缺失／跳过阶段、原生过滤放松、文档范围依赖或无锚的补充属性查询会触发反馈。
编译器可返回 `{"stop":true}` 停止控制；该对象不作为 DSL 查询执行。
重复计划、没有新增事实／原文行或达到三轮也停止；最终仍使用预算40的原生证据包，
不新增向量、实体绑定模型、judge、提取后处理或事实字段。
这是 KITE 原生检索上的有界编译反馈扩展，不能标作未修改原版 c92 的成绩。

2Wiki 已冻结整段库的 1,000 题开发集结果，按官方 v1.1 别名计分为 **EM 68.70%、F1 74.98%**。
109 道触发题用日期核算证据重跑 Answer，891 道沿用已冻结预测。后续对比以
[2WIKI_FREEZE.json](2WIKI_FREEZE.json) 为准，原产物保留，2Wiki 实验暂停。
此前单轮、两轮和三轮的同 100 题对照保留在实验记录。
新组完整建库后先20题审错，再扩100；不会自动扩500。20/100题均为开发集，
不作论文1000题或独立盲测结论。逐轮数值、成本和负面结果见实验记录。

全量任务由 `full-extractive-v1` 开始，格式失败后的接续为 `full-extractive-format-v2`，
建库恢复控制当前为 `full-native-v8`；v5／v6／v7／v8只调整建库故障恢复、检查点和排队，提取提示词一致。
QA候选冻结在 `artifacts/results/multihop/shared-native-bounded-v1/runtime`，原v4为历史对照。
实际阶段以 `artifacts/results/multihop/ACTIVE.json`、进程表和收据为准。共享语料规模：
MuSiQue 11,656 段、HotpotQA 9,811 段、2Wiki 6,119 段，
均为Hi-Q表2的共享支持/干扰池，不按支持标注筛选。每段原文单次提取，优先保留表达完整关系的原句或相连子句；
不增加事实字段或语义后处理。既有 `entity_types` 的提示补充 `group`，表达家族等非组织集合。
抽查仍发现个别实体漏标、同一实体分成多个代码，不能声称提取完全正确。

初始快照在 `artifacts/results/multihop/full-extractive-v1/`，当前统一状态见
`artifacts/results/multihop/full-native-v8/RUN_STATUS.json`。各进程从自己的冻结 `runtime/`
加载冻结代码，以 `KITE_ARTIFACTS_DIR` 指向本 checkout 的 artifact 根目录；每 500 段保存完整原生库检查点，
恢复时优先读取经校验的原生检查点；失败或未落盘部分仍逐段精确重放缓存，不重复请求成功来源。只有已记录且未收到响应的传输失败可按来源补试一次，
旧请求用量保留为未知。`campaign.py` 的进度回调只记录状态，不改变提取结果。

格式恢复版修订了上段“已收到响应不再请求”的治理规则：显式 `--recover-format` 只允许对
**已收到且语法不可解析**的 JSON 补试一次，启用 API JSON mode；提示词及其他模型参数保持不变，
包括 v4 起明确允许的 `finish_reason=length` 截断，不增加输出预算。旧错误响应不进入模型，
不作语义修补或择优。已有完整合法 JSON、语义遗漏、拒答、未知在途
状态或已有额外尝试都不满足该资格。失败来源可能有两次物理 HTTP 请求，须如实统计，不能声称
每段绝对一次请求。新格式参数进入独立缓存指纹，恢复前核验原始提示词 SHA。

`--reuse-from` 可复用已停止构建的成功前缀：失败来源仍保留尝试记录，不作为成功缓存；
复制前获取来源构建锁，运行中的库拒绝复制。2Wiki 已审计复用 278 段，格式恢复仅增加 1 次调用。
MuSiQue / HotpotQA 原冻结进程继续，结束后再接续到统一版本；不打断、不重复提取有效来源。
新队列仍是完整库后各 100 题，旧等待队列已在无推理子进程时停止。格式恢复当时 67 项回归通过，
格式恢复不是精度提升证据；详见实验记录第 12 节及实际进程状态。

`full-native-v3` 将本 benchmark 的 `EXTRACT_STRICT_TOPICS` 恢复为 False，保留严格来源和
JSON 形状检查。未知 topic 按原生 `_resolve_fact_topics` 处理：不造节点、不猜映射，事实仍保留，
允许 topics 为空。manifest／进度显式统计 `empty_topic_facts`，它不是新增的事实字段。
这是撤销额外门禁，不是语义补齐；三个提示词保持逐字一致。已用零 API 重放证明 HotpotQA 前
811 段字段不变，第 812 段 6 条原文事实保留、3 条缺 topic，69 项回归通过。模型漏写 topic 的
质量问题继续记录。运行中的其他来源进程不打断，结束后逐级复用缓存；最终各 100 题只使用统一
profile。完整接续链和真实 PID 见当前 `RUN_STATUS.json`，旧队列的等待状态属于历史记录。

v4 对 2Wiki 第 1,107 段的重复生成截断作了一次相同输入 JSON-mode 小试，得到 20 条事实，
已知新增 4,931 tokens。原始失败的 18,694 tokens 仍计入。小试的同一响应经零网络原生重放入库，
没有再次请求；前 1,106 段原生字段一致。该规则统一用于三组，不按题目或数据集定制。
这是格式恢复，不是语义质量复问；仍有实体长短名称碎裂，未做后处理，70 项回归通过。

v5 为明确记录的终态 HTTP 5xx 补齐最多一次同请求恢复，并从已接受前缀直接计算下一检查点，
避免从第 500 段开始重复重放。v6 另覆盖已核验原进程退出、最后请求未落盘响应的中断：先以
禁用网络的原生缓存重放保存成功前缀，再核对来源、代码、库和收据摘要、单个未知请求及原 PID
确实不存在，才允许最多一次相同请求。缺失证明、仍活着的进程、摘要变化或已经补过一次均拒绝。
原未知用量不作零成本，不补造提供方错误记录；每来源总物理请求仍不超过两次。74 项本地测试、
冻结副本 6 项恢复测试通过。这些属于运行恢复，不是精度改进。2Wiki 原 100 题预测逐字节沿用。

v7 消除正常检查点后从头渲染历史提示词的开销。三组各 5,000 段的原生词表往返保存／加载后，
各自随后 10 段完整提示词缓存命中、事实和后续词表均一致。真实 Mu 8,000 段 XML 往返逐字节
相同；切换只在缓存重放、无新请求在途时执行，成功前缀没有重复付费提取。新第 8,001 段的完整
实际提示词也与原生 8,000 段状态重建结果一致。75 项本地、7 项冻结副本测试通过。Hot 旧进程
继续正常提取，停止后才复用到统一控制版本，不同时开第二个提取进程。

v8 修复损坏JSON被解析器取出内部fact后无法触发格式恢复的问题；仍只允许一次相同提示词的JSON模式格式请求，
不重试合法JSON的坏字段或语义质量问题，不手修事实。76项测试通过。Mu成功8,389段复用缓存，Hot原进程继续。

各组完整建库后，有限队列运行 `n100-native-v1`，每题一次 compile、一次 Answer；按最新用户指示，每组预测全部冻结后即独立评分，不等待其余组。
`review_baseline.py` 在独立、禁用网络的分析进程读取支持标注，对照精确来源段落 ID；仅匹配标题不能证明取到了
正确段落，取得支持段落也不能证明关系链完整。错题与正确题都保留给后续源文核验。队列不会自动扩展到
500/1000 题，必须先做错误归因和统一的小批量方案验证。现有全部 1000 题均为已暴露开发数据。

## 第一阶段：修好现有框架

1. 先用每组 1 题走通全部路径；源语料保留每题所有候选段落及干扰项。
2. 修日期目录与 source 重复造成的开销。Compile 无需目录时不构造/发送目录；
   Answer 同一来源只展示一次，保持已选事实、原先可见原文范围、真实事件日期和引用 ID。
   离线固定计划和证据检查信息保留，再做统一在线复测，不能凭 token 减少声称精度提升。
3. 在同一条路径分析提取遗漏、计划过滤/范围、证据打包、关系方向及最终答案粒度。
   只修实现 bug 和共享提示词；用独立虚构材料检查提示词，不加入真实测试 QA 示例。
4. 逐步扩大到每组 10、100、500、1000 题。小样本候选池只作诊断；论文规模评测需要
   每题检索同一完整共享池。每次扩量前冻结代码、提示词、模型和预算，记录所有失败和用量。
5. 用错误分布及统一复测证明当前框架的残余瓶颈后，才考虑第二阶段。不能用三道题的好坏
   判断到达上限，也不能将 DSL 多阶段计划率称为语义多跳成功率。

## 第二阶段：通用机制

只针对第一阶段已确认、可跨任务复现的限制提出机制；单独开关做统一消融和独立验证。
不按数据集名、题号、标准分解、支持标注、答案长度习惯或真实实体关系写规则；
不把候选答案按单题拼接取最好结果，不在已暴露题上反复择优后称为盲测。
全量重新提取前先核对源文、做小试和独立收益验证，避免无证据地从头消耗 27,586 段调用。

## 评测与论文目标

原始题已经暴露，均标为开发集。推理进程只读 corpus / questions，references 和原始 QA
文件禁止进入推理；每组预测全部冻结后，独立禁网进程计算该组 EM / token F1，不用 LLM judge，
不后处理答案。冻结后标签仅用于评分及离线错误归因。新验证题应在方法冻结后一次使用，
并说明固定语料覆盖条件的限制。

主计分使用固定references；2Wiki为Hi-Q文件提供的canonical answer。其官方aliases/demonyms
只用于冻结后的独立评分侧表，不回填references或进入推理，不当作模型提分。
本实验未核实该表是否采用这些别名；侧表不声称与论文完整流程一致，历史主分保持不变。

论文 2608.30468v1 表 2 的 Hi-Q 目标（共享支持/干扰语料，1000 题/组）：

| 集合 | EM (%) | F1 (%) |
|---|---:|---:|
| MuSiQue | 45.0 | 57.2 |
| HotpotQA | 64.3 | 77.4 |
| 2Wiki | 64.5 | 73.4 |

表 1 是另一档完整语料检索：MuSiQue 139,416 段、2Wiki 430,225 段、HotpotQA 5,233,235 段，
对应 Hi-Q EM/F1 为 37.4/50.6、62.0/71.4、57.4/69.9。不能将小池结果对比该表宣称超过。
论文 reader 同为 4o-mini；本实验 Luna 建库/编译不同于其检索控制流程，成本必须另报。
超过目标须三组统一方法六项达到表 2 且至少一项严格超过，并完成独立验证；不能凭少量题宣称。

## 重复评测

`--tag` 选择数据和库，`evaluate --run NAME` 保存新的不可覆盖结果而复用原库；
原 `score --run NAME` CLI 保留三组全部冻结的门禁；当前队列用独立 `score_group.py` 按组冻结后评分。
每轮保存 manifest、逐题 prediction、完整
API 请求/响应（不含认证头）及已知/未知用量。历史结果永不就地改答案或覆盖重跑。

扩大同一顺序的语料时，`build --reuse-from OLD_TAG` 只复制已完成、来源哈希一致的
严格有序前缀原始响应。已完成且无失败的原生检查点验证来源、顺序、代码、模型和 XML 摘要，
并用首段完整提示词和端点缓存键作门禁，再恢复原生 Vocab（admission=4、promote=3）。
没有可信检查点时，仍逐段核验完整提示词缓存键；未落盘部分也不跳过该核验。
缺失、损坏或提示词变化会在新增 API 调用前停止。manifest 区分复用历史调用与
本次新增调用；总账按原始 call_id 去重。提示词变更的旧提取不能复用为新结果。

## 整段原文索引的存储边界（2026-11-03）

`passage_index.assemble` 无条件保存每段原文为一个原生文档检索记录。
模型元数据校验失败或全局别名登记冲突，只拒收该段生成的元数据；
原文仍能通过现有 units/正文 grep/lines 查询交付。没有标签修补、实体合并或额外模型调用。
审计区分 `documents`（原文入库数）、`documents_with_index`（接受模型索引数）和
`raw_only_documents`（只保留原文数），不得将原文可检索等同于别名或标签已修复。

已有冻结响应可用 `python -m benchmarks.multihop.passage_rebuild --source-run <旧index目录> --output <新index目录>`
离线重建；禁止联网及读取 QA/答案。该验证核对原文、原有索引/词表不变及被恢复文档的原生查询，
不产生新 EM/F1，也不能声称原来答对的题没有回退。历史库与历史评分保持原样。
